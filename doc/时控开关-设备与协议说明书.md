## 1. 一页速览

> **核心结论**
> 时控开关是「纯蓝牙本地控制」设备，**不经过任何服务器**。小程序里的后端 `wechat.isoundtek.com` 只用来下发遥控面板的图片配置，跟通断控制无关。所以只要复刻 BLE 协议，就能完全脱离微信和原厂小程序独立控制。

### 最小可用闭环：4 条指令

| 步骤 | 指令 | 作用 | 必要性 |
|---|---|---|---|
| 1 | `3004` | 读取全量状态（通道数、通断、模式、定时组） | 必需 |
| 2 | `3225` / `3221` | 总开关 / 单通道开关 | 必需 |
| 3 | `3007` | 切工作模式（常关/常开/自动/倒计时/循环） | 必需 |
| 4 | `3234`（或 3231/3236） | 写入定时组 —— 「时控」的本体 | 必需 |

对时 `5001` 强烈建议一并实现：定时靠设备本地 RTC 执行，时间不准等于定时全错。

### 三个必须先确认的点

1. 时控开关有 **30 个型号**，分属 **3 个固件族**，定时报文的指令码和字段数量不同——必须先读到型号再决定用哪条指令。
2. 型号在**广播包**里就带了，不用连上就能判定（见 §3）。
3. 单通道机型的「开关」有两个入口（`3225` 总开关、`3221` 单通道），原厂两处都用；建议以 `3221` 为准、`3225` 做兜底。

## 2. 它到底是什么设备

### 2.1 在目录里的身份

| 字段 | 值 | 说明 |
|---|---|---|
| productName | 时控开关 | 另有「计量时控通断器」2 款、「时控商照」1 款（类型 4957） |
| type | `4951` | 类型名「插座」，图标 `icon-zhinengchazuo` |
| remote | `socket` | 复用「插座」遥控模板，共 36 款设备共用此模板 |
| 型号数 | 30（精确名为「时控开关」） | 见附录 A |

### 2.2 功能集合（来自 socket 页 UI 结构）

原厂把时控开关的功能收在一个页面里的 5 个区块，这也是本文档的编排依据：

| 区块 | 能力 | 对应指令 |
|---|---|---|
| 主控 | 总开关、每路开关、童锁、上电状态、按键密码 | 3225 / 3221 / 3229 / 3020 / 3210 |
| 工作模式 | 常关 / 常开 / 自动 / 倒计时 / 循环定时 / 半秒定时 | 3007 |
| 定时组 | 最多 28 组，每组「时间 + 星期 + 开/关」 | 3231 / 3234 / 3236 |
| 倒计时 | 精确到秒的一次性倒计时，到点执行开或关 | 3232（粗档位用 3224） |
| 循环定时 | 每天同一时段反复通断；另有「半秒定时」用于点动/闪烁 | 3233 / 3235 |
| 计量（部分型号） | 电压/电流/功率/今日与本月电量、上下限保护与延时关断 | 3281 / 3282 / 3171 |

> ⚠️ **注意：不要按「插座」去理解它的行为**
> 时控开关的 `3007` 模式语义与普通插座不同：普通插座 `3007` 是「灯效模式」，而时控开关的 `3007` 是「执行策略」（常关/常开/自动/倒计时/循环）。同一个指令码在不同模板下含义完全不同，这是本项目最容易踩的坑。

## 3. 设备识别码

### 3.1 广播包格式（无需连接即可识别）

设备把身份写在 BLE 广播的**厂商自定义数据**（Manufacturer Specific Data，AD type 0xFF）里：

| 偏移(字节) | 长度 | 字段 | 本设备取值 |
|---|---|---|---|
| 0 – 1 | 2 | type 类型码 | `49 51`（hex 字符串 "4951"） |
| 2 | 1 | encode 生态标识 | `41`（ASCII 'A'） |
| 3 – 8 | 6 | MAC 地址 | 设备实际地址 |
| 9 – 末尾 | n | productId 型号识别码 | ASCII，如 `"ZJSK02"` |

**过滤规则：** `encode` 必须等于 `0x41`，且 `type` 等于 `0x4951`，才是时控开关。非本生态设备的广播不带这段厂商数据，直接丢弃。

#### 真实示例

```
49 51 41 C0 FF EE 12 34 56 5A 4A 53 4B 30 32
│  │  │  └──────┬──────┘ └──────┬──────┘
│  │  │        MAC            "ZJSK02"
│  │  └─ encode = 0x41
└──┴──── type = 0x4951
```

### 3.2 五种「识别码」的区分

| 名称 | 来源 | 示例 | 用途 |
|---|---|---|---|
| 生态标识 | 广播字节 2 | `0x41` | 过滤非本厂设备 |
| 类型码 | 广播字节 0–1 | `0x4951` | 区分插座/灯/加湿器等 33 类 |
| **型号识别码** | 广播字节 9+ | `ZJSK02` | **决定用哪套指令与定时报文族** |
| 显示识别码 | MAC 派生 | `3398` | 给人看的 4 位数字，界面上区分同款多台 |
| 蓝牙地址 | 系统 API | `C0:FF:EE:12:34:56` | 连接时用 |

#### 显示识别码算法

取 MAC 末 4 个 hex 字符 → 转十进制 → 若长度 ≥ 5 取末 4 位，否则左补 0 到 4 位：

```
MAC 末4位 "3456" → 0x3456 = 13398 → 长度5 → 取末4位 → 3398
```

它只是展示用的友好编号，**不参与任何协议字段**，冲突是可能的（不同 MAC 可能算出同一个 4 位数）。

> ✅ **实践建议**
> 扫描时只缓存 `type=0x4951 && encode=0x41` 的设备，用 `productId` 查表得到中文名和报文族，列表里同时展示「型号 + 显示识别码 + RSSI」，用户就能在多台同款设备中一眼认出要连哪台。

## 4. 连接方案（完整时序）

### 4.1 全流程

```
① 扫描广播 ──► 得到 productId / MAC / RSSI，判定型号与报文族
        │
② 停止扫描（必须，否则影响连接稳定性）
        │
③ createBLEConnection  超时 5s，失败重试 ≤5 次
        │
④ discoverServices ──► 找 16 位短 UUID = 9AF4 的服务
        │                （未命中则退化为「同时含可写 + 可通知特征」的服务）
        │
⑤ 特征筛选：第一个 properties.write → 写特征
           第一个 properties.notify|indicate → 通知特征
        │
⑥ 打开 notify（写 CCCD = 2902）
        │
⑦ 等 500ms（链路稳定）
        │
⑧ 发 5011（查询设备信息）
        │
⑨ 等 100ms
        │
⑩ 发 5001 + 当前时间（14 字节 ASCII：YYYYMMDDHHMMSS）
        │
⑪ 收到 5012 ──► 解析 productId + 版本号，修正报文族
        │
⑫ 等 500ms（可选）→ 发 3004 拉全量状态
        │
⑬ 收到 3005 ──► 解析通道数/通断/模式/定时组，渲染界面
```

### 4.2 GATT 细节

| 项 | 取值 | 说明 |
|---|---|---|
| 服务短 UUID | `9AF4` | 完整形如 `00009AF4-0000-1000-8000-00805F9B34FB`；原实现是取 UUID 字符串第 5–8 位比对 |
| 写特征 | 同服务内首个可写特征 | 原实现不写死 UUID，动态发现 |
| 通知特征 | 同服务内首个 notify/indicate 特征 | 收到数据从该特征回调 |
| 写类型 | Write With Response | 逐包串行，上一条写完才发下一条 |
| MTU | 建议请求 185 | 定时表单包可达 200+ 字节，默认 23 必须分片 |
| 连接超时 | 5s，重试 5 次 | 失败后清状态并提示 |

### 4.3 关键延时（不要随便改小）

| 位置 | 延时 | 原因 |
|---|---|---|
| 连接成功 → 发 5011 | 500 ms | CCCD 写入与链路加密尚未完全就绪，过早发送会丢第一包 |
| 5011 → 5001 | 100 ms | 设备要先处理信息查询，紧挨着发会被丢 |
| 5012 → 3004 | 500 ms（原实现） | 实际 100–150 ms 也可用 |
| 定时表分包含间隔 | 100 ms | 设备按包写入 Flash，间隔过短会吞包 |
| 应用层 `5001` 之外的命令间隔 | ≥ 100 ms | 连发多条（如切模式+下发定时）建议中间加延时 |

> ⚠️ **MTU 与分片**
> 原厂实现是「一条指令一次 write」，不分片（微信底层代为处理）。自己做 App 时必须先 `requestMtu`，再按 `MTU-3` 分片串行写，否则定时表（一节最多 10 组、单包 200 字节以上）一定会写失败。

### 4.4 异常处理

- **找不到服务**：等 2s 后断开重连；连续 3 次失败提示「设备不支持或已被他人连接」。
- **写超时**：同一包重试 2 次，仍失败则断开重连并重新握手。
- **断线**：设备会保持原有定时与输出状态（定时存在设备 Flash 里），重连后补发 3004 校准界面即可。
- **时间漂移**：每次连接都发 5001 对时，不要只在首次配对时发。

## 5. 帧协议

### 5.1 帧结构

```
FE 01 | LEN(2B 大端) | CMD(2B) | ARG(nB)

LEN = (CMD 字节数 + ARG 字节数) = 2 + ARG 长度
```

| 字段 | 说明 |
|---|---|
| FE 01 | 固定帧头（SOF） |
| LEN | 大端 2 字节，**只算 CMD+ARG，不含帧头与自身** |
| CMD | 2 字节指令码，如 `3004` |
| ARG | 参数，长度可变；部分指令无参数 |

### 5.2 收包状态机

BLE 一次通知可能只到半帧，也可能粘了两帧。原实现是一个三态机：

1. 若数据以 `fe01` 开头：记下 LEN（第 3–4 字节），累积到 `4+LEN` 字节为止；
2. 若不以 `fe01` 开头且处于收包中：直接续接；
3. 凑满后整帧交给解析，状态归零。

> ❌ **已知缺陷**
> 原实现没有处理「一包两帧」和「帧头错位」。自己做时必须：在缓冲区里搜索 `fe01` 对齐、丢弃无效字节、循环取出所有完整帧，否则连续高频状态上报（如 3005 后紧跟 3221）时会漏包甚至错位。

### 5.3 组帧示例

| 动作 | 完整帧（hex） | LEN |
|---|---|---|
| 查询设备信息 5011 | `fe01 0002 5011` | 0002 |
| 对时 5001（2026-11-18 22:10:00） | `fe01 0010 5001 3230323631313138323231303030` | 0010（16 = 2 + 14） |
| 读全量状态 3004 | `fe01 0002 3004` | 0002 |
| 总开关开 3225 | `fe01 0003 3225 01` | 0003 |
| 通道 0 开 3221 | `fe01 0004 3221 00 01` | 0004 |
| 切自动模式 3007 | `fe01 0003 3007 02` | 0003 |

对时参数就是 14 个 ASCII 数字字符（不是 BCD、不是时间戳）：`YYYYMMDDHHMMSS`。年份用 4 位。

| CMD | 载荷结构 | 含义 |
|---|---|---|

### 6.3 密码报文（3210）

参数是两段 TLV，共 10 字节：

```
02 | 03 20 en | 06 21 p1 p2 p3 p4

02          条目数 = 2
03 20 en    长度3、类型0x20、启用位（01 设置 / 00 关闭）
06 21 p...  长度6、类型0x21、4 位数字的 ASCII
```

示例：设置密码 1234 → `02 03 20 01 06 21 31 32 33 34`，帧为 `fe01 000c 3210 02032001062131323334`。

关闭密码时还必须携带原密码，且要求蓝牙 RSSI 在 −50 dBm 以内（原厂防盗用逻辑）。

### 6.4 5012 设备信息应答

```
ARG = 00 | n1 | productId(n1 字节 ASCII) | n2 | version(n2 字节 ASCII)

例：型号 ZJSK02、版本 1.2.3
  fe01 0010 5012 00 06 5A4A534B3032 05 312E322E33
```

> ⚠️ **原实现有个偏移 bug**
> 微信端在解析 5012 时从 ARG 的第 2 字节开始读，并且在推进指针时少退了 1 个字节，导致版本号偶尔多带一个杂字符。稳妥做法：按上面的结构严格「长度 + ASCII」逐段解析，并把版本号只作为展示用，**不要拿它做逻辑分支**（报文族判断以 productId 为准）。

## 7. 定时组报文（核心）

> **先确定族，再组包**
> 同样是「写定时」，三个固件族用三条不同指令、字段长度也不同。用错指令的表现是：**不报错、但设备不回状态、定时不生效**——很难查。判定依据只有一个：广播里的 productId。

### 7.1 三族对照

| 族 | 指令 | 时间精度 | 单组字节 | 分包含量 | EN 位行为 | 型号 |
|---|---|---|---|---|---|---|
| LEGACY | `3231` | 时:分 | 15 | 单包全发 | 生效 | IS0213、IS0214（时控商照 IS0217 同族） |
| GROUP | `3234` | 时:分:秒 | 19 | 10 组/包 | **被强制写 01，不生效** | 其余 26 款时控开关 |
| BATCH | `3236` | 时:分:秒 | 19 | 1 组/包 | 生效 | DZL002、WZHF10（计量通断器同族） |

### 7.2 单组结构（以 3234/3236 为例，19 字节）

| 偏移 | 字段 | 长度 | 取值 | 说明 |
|---|---|---|---|---|
| 0 | LEN | 1 | `13` | 本组总字节数，**含 LEN 自身** |
| 1 | IDX | 1 | 00–1B | 组序号，从 0 连续编号，用于删除后重排 |
| 2 | EN | 1 | 00/01 | 是否启用（GROUP 族无效，恒发 01） |
| 3 | SWID | 1 | 00 | 通道号，单路时控恒 0 |
| 4 | WEEK_S | 1 | 位图 | 开始日：bit0=周一 … bit6=周日 |
| 5–6 | SH | 2 | ASCII | 开始时，如 08 → `30 38` |
| 7–8 | SM | 2 | ASCII | 开始分，如 30 → `33 30` |
| 9–10 | SS | 2 | ASCII | 开始秒（3231 族没有此字段） |
| 11 | WEEK_E | 1 | 位图 | 结束日，单点定时时与 WEEK_S 相同 |
| 12–13 | EH | 2 | ASCII | 结束时 |
| 14–15 | EM | 2 | ASCII | 结束分 |
| 16–17 | ES | 2 | ASCII | 结束秒（3231 族没有） |
| 18 | EVENT | 1 | 00/01 | 到点动作：00 关 / 01 开 |

**星期位图约定：** `0x7F` = 每天，`0x1F` = 工作日（周一至周五），`0x00` 或 `0x80` = 仅一次。

### 7.3 整包结构

```
[组数 N] 后接 N 个「[LEN][单组]」
```

组数 ≤ 28（`timerMaxCnt`）。删除一组 = 从列表移除后**整体重排 IDX 并重发**；清空全部 = 只发一个组数字节 `00`（如 `fe01 0003 3234 00`）。

### 7.4 真实报文示例

场景：1 组定时，每天 08:30 开、18:00 关。

#### 3234 / 3236（有秒族）

```
载荷（20 字节）：
  01            ← 组数 = 1
  13            ← 单组长度 = 19（含自身）
  00 01 00 7f   ← IDX=0  EN=启用  SWID=0  WEEK_S=每天
  30 38         ← 开始时 "08" (ASCII)
  33 30         ← 开始分 "30" (ASCII)
  30 30         ← 开始秒 "00" (ASCII)
  7f            ← WEEK_E = 每天
  31 38         ← 结束时 "18" (ASCII)
  30 30         ← 结束分 "00" (ASCII)
  30 30         ← 结束秒 "00" (ASCII)
  01            ← EVENT = 开

完整帧：fe01 0016 3234 01130001007f3038333030307f31383030303001
        （LEN = 2 + 20 = 22 = 0x0016）
```

#### 3231（无秒族）

```
载荷（16 字节 = 组数 1 + 单组 15）：
  01                                ← 组数 = 1
  0f                                ← 单组长度 = 15（含自身）
  00 01 00 7f  3038 3330  7f  3138 3030  01
  └ 同 3234，但没有 SS / ES 两段（时间只到分）

完整帧：fe01 0012 3231 010f0001007f303833307f3138303001
        （LEN = 2 + 16 = 18 = 0x0012）
```

> ⚠️ **LEN 最容易算错的一点**
> 3231 的载荷是 **16** 字节（组数字节 + 15），不是 15。少算这个组数字节，帧 LEN 就会写成 0x0011，设备会把整帧当残缺帧丢掉——没有任何错误回包。

### 7.5 下发策略

| 族 | 策略 | 包间隔 |
|---|---|---|
| 3231 | 一次发完所有组（受 MTU 限制时分片） | — |
| 3234 | 按 10 组切包，逐包顺序发 | 100 ms |
| 3236 | 每组单独一包；**删除组时必须补发一条 EN=00 的空组**把旧数据顶掉 | 100 ms |

> ⚠️ **3236 族的删除陷阱**
> 因为一个包只能覆盖一组，直接把 28 组缩成 3 组时，第 4–28 组的旧数据还在设备里。必须对「被删掉的下标」补发 `EN=00` 的占位组，或者记录设备上次上报的组数，逐条覆盖。

## 8. 倒计时 / 循环 / 半秒

### 8.1 倒计时 3232（精确到秒）

```
ARG = 01 | LEN | 00 01 00 00 | SH SM SS | EVENT
       │    │    │  │  │  └ 保留
       │    │    │  │  └ SWID
       │    │    │  └ EN
       │    │    └ IDX
       │    └ 本组字节数（含自身）
       └ 组数恒为 01

SH/SM/SS 为 ASCII 两位数（如 10 分 30 秒 → 3130 3330 3030）
```

示例「10 分 30 秒后关」：`fe01 000f 3232 01 0c 0001 0000 3130 3330 3030 00`

倒计时是**一次性**的：设完之后还要把模式切到 `03`（倒计时），设备才开始计时。

### 8.2 循环定时 3233（每天同时段反复）

```
ARG = 01 | LEN | 00 01 00 00 | sH sM sS | 00 | eH eM eS | EVENT
```

示例「每天 08:00:00 开 → 18:00:00 关」：

```
fe01 0016 3233 01 13 0001 0000 3038 3030 3030 00 3138 3030 3030 01
```

与定时组的区别：循环定时只有一段，没有星期概念，天天执行。切到模式 `04` 生效。

### 8.3 半秒定时 3235（点动 / 闪烁）

用于「通电 0.5 秒、断电 0.5 秒」这类点动场景，周期参数是 **IEEE754 float32**（大端）。

| type | 结构 | 用途 |
|---|---|---|
| 0 | `[IDX][EN][TYPE=00][保留 3B][float32 起秒][float32 止秒][循环次数 2B]` | 周期点动：0.5~2.0 秒反复 N 次 |
| 1 | `[IDX][EN][TYPE=01][保留 3B][sH sM sS][00][eH eM eS][00][循环次数 2B]` | 时段内点动：在指定时段之间反复 |

整包前面同样加 `01` + LEN。切到模式 `06` 生效。

> ⚠️ 时控开关大多数型号不支持半秒定时（原厂 UI 里也只对特定型号显示），**建议不要默认暴露这个功能**，否则用户点了没反应会以为坏了。

## 9. 状态回传解析

### 9.1 3005 外层结构

```
[条目数 N] 后接 N 个条目，每个条目 = [ITEM_LEN][TYPE(2B)][VALUE]
```

`ITEM_LEN` 含自身，所以整条按 `ITEM_LEN` 字节前移；`VALUE` 长度为 `ITEM_LEN − 3`。注意这里的 TYPE 是 **2 字节**，而 3281/3213 里的 TYPE 是 **1 字节**，两者不能混用。

### 9.3 解析要点

- 设备**不会把所有条目都报上来**，只报它支持的。收到什么解析什么，缺失的字段保持本地旧值。
- 定时组只可能出现在 3231 / 3234 / 3236 其中一个条目里，**三选一**，按收到的类型用对应规则解析。
- 时间字段是 ASCII，取低半字节即可还原数字：`"3138"` → 1、8 → 18 点。
- 条目长度字段若为 0 或越界，立即停止解析本包——这是保底防崩，设备偶发截断上报。

### 9.4 数字编码约定

| 编码 | 用途 | 换算 |
|---|---|---|
| ASCII 数字 | 定时时间、密码、设备时间 | 0x30–0x39 即 '0'–'9'；两位一组表示 0–99 |
| Q16.16 定点 | 电量、电压、电流、功率、阈值 | 高 2 字节为整数部分，低 2 字节 / 65536 为小数；展示保留 2 位 |
| IEEE754 float32 | 经纬度、半秒定时的秒数 | 大端 4 字节 |
| 位图 | 星期、电参告警位 | bit0 起对应第一项 |

## 11. 型号族差异与已知坑

### 11.1 差异清单

| 差异点 | 表现 | 处理 |
|---|---|---|
| 定时指令码 | 3231 / 3234 / 3236 三选一 | 按 productId 查表（§7.1） |
| 定时是否含秒 | 3231 族只到分 | 组包时省略 SS/ES 两段，单组 15 字节 |
| EN 位是否生效 | 3234 族被强制写 01 | 停用某组＝删除并重排，不能靠 EN=00 |
| 单包组数 | 3234 十组、3236 一组 | 分包 + 100 ms 间隔 |
| 开关入口 | 部分机型只有 3219（单键），部分用 3221/3225 | 三个都发一遍最稳，或先 3004 看设备报了哪个 |
| 计量能力 | 仅 3281 支持的型号回包 | 未收到 3281 就隐藏电参区 |
| 日落功能 | 仅部分型号（如时控商照 IS0217） | 未收到 3261 就隐藏 |

### 11.2 五个容易踩的坑

1. **LEN 的算法**：是 `(CMD+ARG) 字节数`，不含帧头也不含自身。算错会让设备整包丢弃，且没有任何错误提示。
2. **时间是 ASCII 不是 BCD**：08:30 是 `30 38 33 30`，不是 `08 30`。这一点错会导致定时时间变成乱值。
3. **组长度字节含自身**：单组 LEN 写 19（不是 18）。少 1 会让设备把下一组的首字节当成自己的尾巴，整表错位。
4. **模式与定时是两件事**：写完定时组如果模式还停在「常关」，设备不会执行。切 `3007=02`（自动）才生效。
5. **删组要整体重发**：只发一条"删除"没有这种指令，一律是「改列表 → 重排 IDX → 全量重发」。

### 11.3 界面语义建议

| 用户操作 | 实际下发 |
|---|---|
| 开/关 整个设备 | 3221 (通道0) 或 3225；同时把模式切到 01 常开 / 00 常关 |
| 启用定时 | 3234 写表 + 3007=02 自动 |
| 临时手动开一下 | 3221 单路开，模式保持 02，到下一个定时点设备会自动纠正 |
| 倒计时 30 分钟关 | 3232(00:30:00, event=0) + 3007=03 |

## 13. 手工验证步骤

有设备时，用 nRF Connect（Android）按下面顺序 15 分钟就能确认全部结论：

1. 扫描，找到广播里带 `0xFF` 厂商数据的设备，记下 type / encode / MAC / 尾部 ASCII → 对照 §3 验证型号。
2. 连接，找短 UUID 为 `9AF4` 的服务，打开其 notify 特征。
3. 写 `fe01 0002 5011` → 应回 5012，核对型号与版本。
4. 写 `fe01 0010 5001 + 当前时间 14 位 ASCII` → 无回包属正常。
5. 写 `fe01 0002 3004` → 回 3005。把载荷按 §9.1 拆开，记录设备实际报了哪些 TYPE。
6. 写 `fe01 0003 3225 01` → 继电器应吸合；再写 `...00` 释放。
7. 写 §7.4 的完整定时帧（先 3007=02）→ 再发 3004，看回包里的定时组是否与所发一致。
8. 把这三步结果记下来，就能确定该型号属于哪一族、开关走哪个入口。
